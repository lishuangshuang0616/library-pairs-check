# 当前工作区 v0.4 评估（2026-11-10）

评估对象为当前未提交工作区，未修改生产代码。20 项单元/集成测试、clippy 和 fmt 检查通过。测试通过仅说明已覆盖行为正确，不构成真实文库的灵敏度和特异度验证。

## 单对输入

当前在两侧数量达标且存在交集时返回 single_candidate_unresolved；不会因为只有一个候选就确认匹配，这是合理设计。目标应是检验技术文库配套证据，而非证明供者或生物学身份。

建议全量扫描，核对结构、有效率、深度及支持量过滤损失，联合查看共有完整双段 barcode、双向集合/reads 覆盖率、Jaccard、cosine。没有经真实数据校准的通用阈值；低交集也可能来自浅测序、错误结构或严格过滤。

可研究单对背景模型：设 A/B 为达标 barcode 集合，在 1536²=2,359,296 种组合均匀、独立使用的理想模型下，随机交集期望为 |A||B|/2,359,296。这个模型只能作解释性基线。真实 barcode 使用偏好、CB1/CB2 关联、批次、背景及 PCR 会违反假设，不能将其显著性直接解释为匹配概率。

没有历史背景时，可尝试保留 oligo 内部计数结构、随机重标记两段白名单编号构造探索性零分布；它仅检验指定的可交换性假设，不能替代真实负对照。不要打乱 read 顺序或只洗牌已有完整 barcode 的计数来检验集合交集：集合本身不会改变。

正式支持单对判定，需要已知正确配对与不同样本错配的历史数据，覆盖批次、深度和试剂版本，按样本/批次分离校准与验证数据，报告假阳性率、召回率及无法判定比例。最终保留“支持配套 / 疑似不配套 / 证据不足”，不要强制二分类。

## 可复现的算法风险

构造每库 100 个达标 barcode、每 barcode 3 reads：cDNA 与候选 A 仅共享 1 个，与候选 B 无交集。程序实际输出 A 为 metrics_agree_unvalidated，目录相同则 assessment=expected_pair_supported。此时双向覆盖率与 cosine 仅 0.01，Jaccard=1/199。说明三个相关指标的一致领先只表示相对排名；缺少绝对证据、背景校准和有实际意义的领先幅度。增加候选数量并不能解决这个问题。

三个指标都依赖同一份 barcode 交集，不是三项独立验证。默认 Q20 为每个 barcode 碱基均达标；min_support=3 为 reads 支持量，不是独立分子量，PCR 重复可放大支持。Top 10000 在大量相同计数时使用固定 barcode 排序，也不能作独立强证据。

## 当前性能

Apple M3、16 GiB，release --locked；合成数据、热缓存、每项重复 3 次，时间取外部进程墙钟中位数，RSS 取最大值。总条数为所有输入 R1 记录之和。原始数据：benchmarks/assessment-2026-11-10.json。

| 情形 | 总 R1 | 每库观察 barcode | 单线程 秒 / MiB | 并行 秒 / MiB |
|---|---:|---:|---:|---:|
| medium gzip | 200 万 | 20 万 | 0.383 / 19.92 | 0.223 / 23.02（2线程） |
| large gzip | 360 万 | 60 万 | 0.823 / 70.98 | 0.477 / 86.83（2线程） |
| singleton gzip | 200 万 | 100 万 | 0.675 / 140.06 | 0.398 / 172.55（2线程） |
| 单样本8 lane文件 | 800 万 | 20 万 | 1.468 / 21.95 | 0.360 / 72.48（8线程） |

前3项均只有2个输入文件，请求8线程实际也只有2线程。最后一项脚本虽命名 four_by_four_gzip，实际只有一个 cDNA/oligo pair，非16次交叉比较；内容使用硬链接重复，仅用于实现压力测试。单次小数据受启动开销影响，不纳入主表。合成序列/质量高度可压缩，不能直接外推真实 FASTQ 或网络磁盘耗时。按本次单线程合成吞吐约300–550万 R1/秒，合计1亿 R1仅扫描量级约18–33秒；这不是生产承诺，实际应以真实文件阶段计时推算。

## 资源与优化顺序

扫描主要随总 reads 线性增长；每对比较遍历 cDNA 计数表，n个样本交叉比较约 O(n²B)，另有 Top 集合交集。rank 和 pairings 对每个 cDNA 重复过滤整个 n² pair 数组，还有 O(n³) 的遍历开销。当前基准未验证多样本扩展性。

内存随所有文库的不同 barcode 数、局部计数表、合并表和待合并结果增长，不随 FASTQ 字节数直接增长。过滤发生在合并完成后，所以 singleton 最终全部被丢弃仍产生高峰。absorb 在首文件也重新建立合并表，造成可避免的双表峰值。并行使用无界 mpsc::channel，若合并赶不上扫描，已完成计数表可能积压，线程数不是严格的结果表内存上限。

scan_wall_seconds 实际包含合并和 assemble 时间，merge_seconds 是其中一部分，不能把两者相加作为独立阶段时间。

建议优先级：

1. 先建立真实正负对照、单对背景证据与校准；避免把弱领先误读为匹配。
2. 低成本修正资源可预测性：有界结果通道；首个局部表直接接管；明确计时字段重叠；增加真正多样本基准。
3. 多样本瓶颈实测出现后，再按 cDNA 分组保存 pairs，比较时遍历较小集合，必要时并行比较。
4. 只有高复杂度计数表成为实测瓶颈时才考虑把白名单映射到紧凑编号，使用稠密计数数组。1536² 个 u64 约18 MiB/表，适合高占用但对稀疏文库可能更浪费，不能一律替换。

结论：值得继续做成文库配套质控工具；下一阶段主要投入正确性校准与单对证据模型，当前没有依据投入大规模底层性能重写。
